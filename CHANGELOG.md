# Changelog

## 0.0.1 — unreleased
- Empty extension skeleton: activates on C/C++ files, `SCA: Show Info` command.
- Unit tests (Mocha) and integration tests (@vscode/test-cli).
- `Finding` model in `src/core/finding.ts`: rule ID, message, file, 1-based range, certainty (definite / possible), severity, source, status (open / justified); validation, sorting, stable key and summary counts. Unit-tested.
- Issue Monitor: own "SCA" view in the Activity Bar (monitored file → findings, definite / possible / justified icons, click to open the line) and matching editor diagnostics (squiggles + Problems panel), both fed from one issue store (`src/core/issueStore.ts`). Empty until checks exist.
- Shield icon for the SCA view container.
- Monitor: "SCA: Add to Monitor" / "Remove from Monitor" / "Remove All from Monitor" for C/C++ files and folders (Explorer, editor and tab menus, Issue Monitor buttons, command palette). Folders expand to their C/C++ files (setting `sca.monitor.exclude`). The monitor is saved per workspace. `Analyzer` runs the list of checks (empty for now).
- Run on save: monitored files are analyzed on every save, autosave included. Waits `sca.analysis.debounceMs` (default 300 ms) and restarts the wait on each new save; a newer run of a file cancels the older one (`src/core/scheduler.ts`). Setting `sca.analysis.runOnSave`. New C/C++ files in a monitored folder are picked up when created, renamed or deleted in VS Code.
- `SCA: Analyze Now` command (also a ▶ button in the Issue Monitor).
- Status bar item: "SCA: analyzing…" / "SCA: N issues"; click opens the Issue Monitor.
- Parser layer `src/core/parser/`: C and C++ syntax trees with tree-sitter (web-tree-sitter + tree-sitter-c / tree-sitter-cpp, WASM, no native build). Grammar picked by extension (`.h` = C). Helpers: `walk`, `nodeRange` (1-based ranges). Checks get the tree through `SourceContext.parsed`. The tree is built before preprocessing, so macros are not expanded.
- Packaging now includes the `web-tree-sitter` runtime; the grammar `.wasm` files ship in `out/parsers`.
- First check `runtime-bugfinder:div-zero` (`src/core/checks/divByZero.ts`): definite for a constant 0 divisor; possible for a parameter divisor with no guard that rules out 0 (if / else / loops / `?:` / `&&` / `||`, early exit, `assert`). Quiet on reassigned parameters, functions with parse errors, and `static` functions whose callers all pass non-zero constants. Samples with DEFECT / SAFE markers in `tests/samples/div_by_zero_cases.c`, checked by a unit test. On car-control: 3 of the 6 planted div_zero defects found (the 3 parameter cases), no false positives.
- Coding-rule checks `sca-own:switch-default` (switch without default; nested switches checked on their own) and `sca-own:goto` (every goto), in `src/core/checks/codingRules.ts`. Definite, severity warning. Sample `tests/samples/coding_rules.c`.
- Headless benchmark `npm run benchmark -- <project>` (`src/bench/`): runs all checks, compares with `expected_findings.csv` and prints found / missed / false positives on SAFE lines / unmarked findings per category, plus the categories without a check. `--json`, `--fail-on-fp`. car-control: 7 of 10 found, 0 false positives.
- Compile database: `compile_commands.json` (found in the root, `build/`, `out/`, `cmake-build-debug/` or set in `.sca.json`) gives each file its include paths and defines (GCC/Clang flags; MSVC `/I /D /U /FI` for cl and clang-cl).
- Small preprocessor for analysis: `#if / #ifdef / #ifndef / #elif / #else` evaluated, inactive branches blanked (line numbers unchanged), unknown conditions keep both branches, include guards recognized; `#define / #undef / #include` followed through the include paths. Checks resolve macro constants (`x / CELLS`).
- Project config `.sca.json` (JSON schema with completion): rule sets and single rules on/off, severity override, excludes, compile database path, extra include paths and defines, deviations. Changes re-check monitored files.
- Justifications: `sca-justify(<rule>): reason` comments (same line or comment line above) and `deviations` in `.sca.json` mark findings as justified.
- Baseline: `SCA: Save Baseline` / `SCA: Clear Baseline` (`.sca-baseline.json`, matched by file, rule and line text); only new findings are shown; setting `sca.baseline.enabled`.
- Issue Monitor icons follow severity (same as the Problems panel); certainty shown in the text.
- Speed: checks use tree-sitter's native node search; results cached by content and project version. 5,000 files ~7 s cold, ~2 s cached. `npm run perf`.
- Reports: `SCA: Export Report` (HTML, CSV, SARIF 2.1.0) and headless `npm run analyze -- <project> --format ...` with `--fail-on` and `--baseline`.
- CI: GitHub Actions (tests on Linux and Windows, car-control benchmark with `--fail-on-fp`, speed test, SARIF and `.vsix` artifacts).
- Value engine (`src/core/engine/`): control-flow graph for C functions (if, loops with the first round peeled, switch with fall-through, goto, break, continue, return), value ranges with a zero witness, set / not set / maybe set, pointer null / not null / maybe null; a fixed-point solver with widening at loop heads; conditions narrow values on each branch. File summaries: stores to `static` objects, return values of same-file functions, constant arguments of `static` functions, computed only when a finding depends on them. Unknown values (other files, fields behind pointer parameters) never give a finding. Time budget: 4,000 block visits / 60 ms per function, 1.5 s per file; over budget is skipped quietly.
- `runtime-bugfinder:div-zero` rebuilt on the engine: also locals, loop counters, static objects (memset, unchecked stores, also through pointers like `t->period_ms`) and same-file return values; definite when the divisor is always 0 at that point. Messages name the source of the 0. New samples `tests/samples/div_by_zero_engine.c`. car-control: `div_zero` 5/6 (was 3/6), 0 false positives.
- Run-time checks on the engine (`src/core/checks/runtime.ts`), one solve per function for all of them: `null-deref`, `uninit-read`, `out-of-bounds` (index, unsigned wrap below 0, memcpy / memset / memmove past the end), `overflow` (signed arithmetic, narrowing signed casts), `uint-wrap` (counter steps), `invalid-shift`, `conversion` (negative to unsigned), `dead-code` (never-taken branches, unreachable code), `endless-loop`, `stack-escape`. Coding rules `sca-own:switch-fallthrough`, `sca-own:unchecked-return`, `sca-own:invariant-condition`.
- Engine: range bounds know whether the code backs them (constants, parameter types, conditions) or not (unknown values, widened loops); only backed bounds give findings. Headers are read for typedefs, struct fields with array sizes, enum values, globals, prototypes and register macros (cached per header). Narrowing through `x - k`, unsigned casts and sums (`addr + len <= N`); `x >= e` facts for `x -= e`; `ARRAY_LEN`-style macros and `sizeof` of arrays; parameters of `static` functions from the argument values at their call sites. Sample `tests/samples/runtime_checks.c`.
- car-control: 36 of 44 expected issues in the covered categories, 0 false positives. 5,000 files ~20 s cold.
- `SCA: Show Control-Flow Graph`: the graph of the function at the cursor, with the values at the start of each block.
- Faster macro lookups (cached values). 5,000 files ~9.6 s cold with the engine.
- Rule catalog: `runtime-bugfinder` and `sca-own` marked as implemented, with `implementedRules`. Catalog text reworded to describe SCA on its own.
- Rule registry (`src/core/rules/registry.ts`): every rule with a title, a description in our own words, why it matters, how to fix it and a bad / good example (examples are tested). Rules can be off by default (`sca-own:magic-number`, `sca-own:increment-in-expression`); `.sca.json` "rules" turns them on.
- Rule help: hovering a finding shows the rule's summary and fix with an **Explain rule** link; `SCA: Explain Rule` (editor menu, Issue Monitor, palette) opens the rule's page. Issue Monitor tooltips show the rule title.
- Coding rules, expressions: `float-equality`, `assignment-in-condition`, `assignment-as-value`, `side-effect-in-logical`, `increment-in-expression`, `comma-operator`, `operator-precedence`, `sizeof-side-effect`.
- Coding rules, control flow: `missing-braces`, `empty-body`, `else-if-without-else`, `loop-float-counter`, `loop-counter-modified`, `switch-too-few-cases`, `switch-on-boolean`, and `recursion` (direct and indirect, through the file's call graph).
- Coding rules, types and literals: `octal-constant`, `lowercase-suffix`, `unsigned-suffix`, `implicit-conversion`, `signed-unsigned-compare`, `signed-bitwise`, `vla`, `bitfield-type`, `int-division-to-float`. They use the type a value has before integer promotion (`u8 + u8` stays `u8`, constants adapt to the other operand).
- Coding rules, declarations: `unused-variable`, `unused-parameter`, `shadowing`, `missing-volatile` (data shared with an interrupt handler), `internal-linkage` (only when every quoted include is found), `dynamic-memory`, `magic-number`, `empty-parameter-list`.
- Metrics `his-metrics:`: `cyclomatic`, `nesting`, `statements`, `parameters`, `returns`, `calls`, `comment-density`, with limits in `.sca.json` "metrics". Severity info.
- Optional external backends: cppcheck and clang-tidy, turned on in `.sca.json` "backends" (path, args, timeout). They run as separate processes on source files; a finding that matches an SCA rule on the same line is merged into SCA's finding (source `sca-native+cppcheck`), others keep the tool's ID and go through the same rule settings, justifications and deviations. `SCA: Check Backends`. `npm run analyze` runs them (`--no-backends`), `npm run benchmark` only with `--backends`.
- Generated catalog: `npm run catalog` writes `catalog/rules.json`, the implemented rules in `catalog/rulesets.json`, the status in the catalog README and coverage page, and the rule reference `docs/rules.md`; a unit test fails when they are out of date. `his-metrics` is now marked implemented.
- Fix: `sca-own:switch-fallthrough` read the text between cases at the wrong place after an inactive `#if` block (offsets of the preprocessed text were used on the original text). Regression test added.
- Checks receive the project config (`SourceContext.config`); the preprocessor reports quoted includes it could not find.
- car-control: 55 of 63 expected issues in 37 covered categories, 0 false positives (all 27 coding-rule issues found). 2,000 files ~11.5 s cold (~6 ms per file).
- Fix: backend findings were dropped when the analyzed file was given by a Windows short (8.3) path or a symlink, because the tools print the real path; paths are now compared after resolving them. CI annotates each failing unit test.
- Memory lifetime checks on the value engine (`runtime-bugfinder:`): `memory-leak`, `double-free`, `use-after-free`, `bad-free`, `dangling-pointer`, `unchecked-alloc`, `alloc-size`, `sizeof-pointer`, `pointer-arith`. Pointer values carry the memory block they point to (an allocation from `malloc` / `calloc` / `realloc` / `strdup`, what a `static` pointer held at the start of the function, or a local array); the state keeps each block's status (allocated, freed, freed on some paths, handed on). Memory stored in an object, passed to an unknown function or returned is never reported as leaked. A same-file function that returns memory it allocated gives the caller a new block (`leak_from_helper()` style). A NULL test on one pointer also applies to its copies (`cur = base; if (base == NULL) return;`). Sample `tests/samples/memory_checks.c` with DEFECT / SAFE markers.
- car-control: 64 of 72 expected issues in 46 covered categories, 0 false positives (all 9 memory categories found). 2,000 files ~12.7 s cold.
- Function and value checks (`runtime-bugfinder:`): `missing-return` (a path of a non-void function reaches the end without `return`), `invalid-enum` (a cast to an enum of a value outside its constants; enum types now carry their values), `no-return-call` (a call to a same-file function that can never return and is not declared `_Noreturn`), `bad-function-pointer` (a call through a function pointer cast from a data object; fixed integer addresses are allowed). The engine treats calls to functions that never return as the end of the path, so `if (!p) fatal(); *p` is not a null dereference. Sample `tests/samples/function_checks.c`.
- car-control: 68 of 76 expected issues in 50 covered categories, 0 false positives.
- String and format checks (`runtime-bugfinder:`, `src/core/engine/strings.ts`): `string-overflow` (strcpy / strcat / sprintf into a char array of known size with an unchecked source, a literal that does not fit, strncpy with a count above the size), `missing-terminator` (strncpy that may fill the whole array without a terminating 0 on the next line), `overlapping-copy` (memcpy between overlapping parts of one array, strcpy / sprintf that read their own destination), `format-mismatch` (printf-family conversion that does not fit its argument, or a missing argument), `uncontrolled-format` (a variable as the only format argument, outside `...` wrappers). Sample `tests/samples/string_float_checks.c`.
- Floating-point checks: `float-overflow` (exp of an argument that can pass the overflow limit), `float-invalid` (sqrt of a negative, log of 0 or a negative, acos / asin outside [-1, 1]), `float-conversion` (float cast to an integer type that cannot hold it; a float with no known bound only against types below 32 bits). Float macro constants (`#define K 0.9f`) now have values; `x * x` is never negative; sqrt / exp / fabs results are never negative.
- car-control: 77 of 85 expected issues in 58 covered categories, 0 false positives.
- Cross-file knowledge: a project index (`src/core/project/projectIndex.ts`) gives each file the return values of functions defined in other files, the argument values and array lengths of all calls in the project (a NULL some caller passes; the buffer length callers pass for a pointer parameter; a length parameter when every call passes exactly the length of its array), and explicit 0 values that initializers put into struct fields (used for a struct copied from elsewhere, `wcal = *calib`). A NULL return that only some arguments lead to is not used; functions defined in more than one file give no facts. A cheap text scan finds the candidate files; facts are cached per file content and redone when a source file is saved, created or deleted (extension) — the CLI, benchmark and speed test use the index too. Time spent on other files is left out of the per-function and per-file budgets.
- Inputs: reads of volatile objects (hardware registers, `volatile` struct fields) and fields behind pointer-to-const parameters get the full range of their type as backed bounds (no zero witness). Fields behind pointer parameters that the function sets are followed (and narrowed by conditions) until a call or a new pointer value.
- Engine: a few narrowing rounds after the fixed point take back loop bounds that widening dropped (`while (i < n - 1 && ...) i++; ... ys[i + 1]`); a block the fixed point reaches stays reachable.
- Accumulators (`runtime-bugfinder:overflow`, `src/core/checks/accumulate.ts`): a signed variable multiplied by a constant >= 2 in a loop with no iteration limit that never compares it; a signed field or global that lives across calls and adds a full-width computed step while nothing in the project compares or limits it. Sliding windows (`sum -= old`) and narrower steps are not reported.
