How it works

One catalog, several checking engines

Like Polyspace, users switch whole rule sets or single rules on and off. Behind each rule, SCA calls the best tool for it.

Config.sca.json or VS Code settings: rule sets on/off, single rules, limits, deviations
→
CatalogRule ID → backend, coverage level, ISO 26262 topic, own description
→
BackendsSCA native · clang-tidy · Clang Static Analyzer · Cppcheck (+ MISRA addon) · Frama-C (optional)
→
ResultsSquiggles in the editor, SARIF for CI, compliance report
  • Deviations: an accepted finding with a written reason and approver — needed for safety audits.
  • Licenses: GPL/LGPL tools run as separate processes; their code is never copied into SCA.
Legend

Coverage levels

LevelMeaning
FullAll tool-checkable rules of the set can be covered.
PartialA useful subset is covered with existing tools; the rest is missing or approximated.
Own checksNo free tool covers it. We must write the checks ourselves — later phases.
Not coveredOut of scope for now. The reason is always written down.

Even "Full" never means 100% of a standard: some MISRA directives are about process or documentation, and some rules are mathematically undecidable — every tool, including Polyspace, can only approximate those.

Gaps

What we cannot cover — and why

Not covered

Proof of absence of run-time errors

What Polyspace Code Prover does (green / red / orange code).

Needs a full abstract-interpretation engine — years of expert work. Frama-C Eva can be plugged in later, but it is C only; no mature open-source option exists for C++.

Not covered

Tool qualification (ISO 26262-8)

Evidence that the analyzer itself can be trusted.

Requires a validated test suite per rule, known-limitations list, controlled releases, and usually an independent assessment (e.g. a certification kit). A process and cost topic, not just code.

Not covered

Concurrency analysis

Data races, deadlocks, shared variables between tasks and interrupts.

Needs a whole-program model of tasks/ISRs, which depends on the OS/RTOS. Free tools are weak here. Later phase.

Not covered

JSF AV C++

Aerospace coding standard.

Not needed for automotive and superseded by MISRA C++:2023.

Limited

Official rule texts

MISRA / AUTOSAR wording in messages.

Copyrighted. We use rule IDs and our own descriptions; users who own the standards can load the official texts locally.

Limited

Undecidable & process rules

Some MISRA rules and directives.

Undecidable rules can only be approximated by any tool; process/documentation directives need human review, not a checker.

Roadmap

Suggested order

  1. Catalog + configuration — load the catalog, rule sets on/off in settings, deviations. No checks yet.
  2. First real findings — run Clang Static Analyzer / clang-tidy on the open file, show squiggles. Run-time bug finding + CERT subset.
  3. MISRA C:2012 — Cppcheck MISRA addon as a backend, rule mapping, own checks for gaps.
  4. HIS metrics — native SCA checks with configurable limits.
  5. Reports — SARIF output and a compliance report (rules checked, findings, deviations).
  6. C++ standards — MISRA C++:2023 / AUTOSAR: map clang-tidy overlap, then own checks by priority.
  7. Later / optional — Frama-C Eva for C proofs, concurrency, tool-qualification evidence.
Summary

Bottom line

  • SCA can offer Polyspace-style rule selection with a catalog and configurable rule sets.
  • With free backends we reach good coverage for MISRA C, CERT, metrics and bug finding.
  • MISRA C++ / AUTOSAR need our own checks — the biggest development effort.
  • Proofs (Code Prover-style), concurrency and tool qualification are not covered now — each for a clear reason.
  • SCA can support ISO 26262 work; it does not make code compliant by itself.
